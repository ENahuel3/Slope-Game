# Slope (modded)

**Play it here: https://enahuel3.github.io/Slope-Game/**

A modded fork of [cgolden15/Slope-Game](https://github.com/cgolden15/Slope-Game), which is a self-hostable copy of the Slope game by Y8 Games / IDnet. This fork lives on the `mod` branch and is what GitHub Pages serves.

## What the mod changes

- **No ads, no tracking.** The page shell is a plain HTML5 document with the ad slots, analytics and promo banner removed, and `TemplateData/mod.js` blocks the game's own calls to the id.net / y8 / Unity Analytics backends before they leave the browser. The in-game app-store button and the Y8 "more games" branding are disabled inside the scene data (`Build/slope_data.unityweb`). A stray token at the end of `unityloader41.js` that threw a `ReferenceError` on every load is fixed.
- **Mod Menu.** All controls live inside **Mod Menu**: Courses, Style and intensity, Light, Music, Track, Mort, King Julien, Version and Fullscreen. The compact menu button stays visible during play. The menu supports keyboard navigation, Escape, and small screens. Preferences persist in the browser.
- **Stacked courses, instantly.** Type a number into **Courses** and every run starts with that many random courses sitting exactly on top of each other: the rapid-Enter restart glitch turned into a feature, built in a fraction of a second while the ball is still dropping into the start tunnel. Changing the number applies at the next restart. The stack applies on a straight track only: hidden courses are built in one frame and cannot follow a rolled lane, so with *Curves* or *Twists* on, the number is dimmed and one course is played (the straight hidden lanes used to cut through the rolled lane and wedge the ball).
- **Instant restarts.** Press **R** at any time to restart with a fresh stack. When the ball dies the mod shows the death for half a second and restarts with the stack rebuilt; there is no game-over screen and no Enter to press. With Courses set to 1 a death goes through the normal game-over screen. A ball that cannot move forward (wedged between two stacked courses at a section drop, where it sits alive in the gap, or in a kink of a rolled lane) never dies, so in a stack or a track mode the mod restarts the run after 1.5 s without forward movement, or after 2 s of creeping (under 5 units/s along the course, a ball wedged between a rolled lane and a hidden straight one), like a death; a plain single-course game is left alone. The watchdog allows four seconds after startup regardless of refresh rate and ignores hidden tabs or frame gaps, so loading or returning to the tab cannot falsely reset a run. Late music-start confirmations do not rebuild an already-live stack.
- **Music.** Original, *Aria Math (Phonk Remix)*, *Mort Jackson – Billie Jean* or *Epic Sax Gandalf* (Ukes of Hazzard). A custom track keeps its place across restarts (it pauses when the game would stop its own track and resumes when a run starts), and switching mid-run is immediate.
- **Track shaping.** The course rolls about its own centre line, as real, continuous geometry. *90° twists* roll a quarter turn over twenty blocks; *Curves* roll 120 to 240 degrees, one block at a time, so you ride up onto what was the wall, over the ceiling and back. Two copies of the lane-block prefab are added to the scene bundle whose surface and neon walls are helicoids twisting by exactly +4.5° / -4.5° from start to end (`tools/patch_roll.py`, meshes generated from the block's shape, collision cooked at runtime), so a run of them is one smooth ribbon and the next block starts where the last ended. The spawner's lane-block spawns take their prefab from a new FSM GameObject variable (`ModBlock`); the mod decides for each upcoming block whether it is flat or a helicoid in either direction and writes that prefab's object pointer, together with the block's start rotation (`ModQ1` and the spawn transform), before the block is spawned. Every spawner step is gated so exactly one step runs per mod frame while a track mode is on, whatever Unity's update rate: the step takes its `Wait` time from `ModHold` (0 = the vanilla one-frame burst, which stacking relies on; 1000 s = hold) and the mod releases one step per frame by zeroing it; a `ModMark` flag tells the mod which steps spawned a helicoid-capable block so the roll only advances across those (tilted, thin and dogleg pieces stay rigid at the roll they were spawned at). The ball's frame follows the built course exactly: each block record carries its start and end roll, gravity, the forward push and steering are rotated into that frame through the WebAssembly heap, and native camera actions follow the current ball position with a rotated offset and quaternion in LateUpdate, so the view stays aligned through twists and rolls (`tools/patch_camera.py`). `tools/patch_spawner.py` / `tools/patch_rotations.py` make every block copy the spawner's rotation, `tools/patch_sections.py` splits the spawner's section states into one step per block, `tools/patch_triggers.py` repairs the checkpoint triggers for the rolled spawn frame, and `tools/fsmparse.py` / `tools/fsmwrite.py` are the PlayMaker FSM parser and serializer behind all of it. The HUD **Track** selector offers Straight, Curves, 90° twists, or both.
- **Scenery toggles.** Turn **Mort** on to show a crowd of Mort from Madagascar with any soundtrack. With Mort off, Aria Math shows a horde of Minecraft's own zombie (the game's geometry and skin, see `tools/assets/zombie/README.md`) and other tracks show the original pillars. Mort now uses the textured [Mort V2 model by calvinwil5782](https://sketchfab.com/3d-models/mort-v2-763eecc8409145059cff213fa646d4cd), under CC BY 4.0, with its original face/body, tail and hair textures. It replaces the stylized Warehouse model and the earlier procedural spheres. Character: DreamWorks Animation. There are 87 Morts per chunk, using three staggered instances of the 29-figure mesh to stay within the engine's 16-bit mesh limit without tripling the download; every Mort stands 240 units from the lane center on either side and turns 20° inward toward it; zombies keep their neon-outline material. The independent **King Julien** toggle puts his PNG face/crown inside every red obstacle border, or restores plain red textures immediately, with any soundtrack. PNG source and implementation: [`TemplateData/themes/julien/README.md`](TemplateData/themes/julien/README.md). The Mort setting and music choose the prefab through the existing `ModBuilding` FSM variable; new figures appear in newly spawned chunks, or after restarting. Model attribution and rebuild instructions: [`tools/assets/mort/README.md`](tools/assets/mort/README.md).
- **Coins.** Collectable 3D coins sit in the places that are hard to reach: on the ridge of the red-striped arch tunnels and on the beam atop the death tunnel's stepped roof, high in the air over the jump lips and the gap (only a fast ball flies that high), at the edges of the thin lanes, on the high edge of the tilted lanes, at the outer corners of the doglegs, and at the very edge of one lane block in three. The counter in the top bar counts the run (best run remembered); the **Coins** toggle in the Mod Menu turns them off. The coin is plaggy's CC0 "gold coin blank" from OpenGameArt (`tools/assets/coin/README.md`), drawn the way games did around 2000: per-vertex Gouraud lighting with a hard specular, an unfiltered 128 px texture, spinning and bobbing in place, with a square-wave two-note chime when picked up. `TemplateData/coins.js` finds the pieces without touching the scene: every track piece is its own draw call with its own object-to-world matrix, and the vertex buffers are uploaded byte for byte from the scene data, so each mesh is recognised by the size and a hash of its upload (`tools/mesh_fingerprints.py`); a piece's coins are laid out in its own lane frame and transformed by its matrix, so they follow a rolled or shifted piece exactly, and the ball (another draw call) gives the position for collecting and the camera for drawing. The coins are drawn into the game's frame after its draws and before the post-processing (`SlopeShaders.onScene`), depth-tested against the lane and the tunnels. One thing in the scene data changed for this: Unity's dynamic batching is turned off (`tools/patch_batching.py`), because it merged the small lane meshes, the jump gap, the thin and the tilted lanes into per-frame combined buffers that no longer named their pieces. `tools/coin_check.py` is the harness: it checks that pieces are recognised, coins are generated and drawn without GL errors on WebGL 1 and 2 and under the lit modes, that a coin planted on the ball's line is collected, and with `--watch` it photographs the coins on each piece kind as the ball reaches it.
- **Visual styles.** *Classic*, *Rainbow* (the green neon becomes a diagonal rainbow that scrolls across the screen and ripples with a travelling wave; red stays red), *Neon glow* (bloom), *Synthwave* (magenta/cyan grading, glow, chromatic fringe, faint scanlines), *CRT arcade* (curved screen, scanlines, phosphor mask), *Hyperspeed* (radial blur and colour split that grow with the ball's speed), *Pixel* (chunky dithered pixels), *Noir* (black and white with the red obstacles kept) and *Matrix* (green phosphor). They are post-processing passes over the finished frame; see *The shader system* below.
- **Lighting.** *Normal*, *Sunny* or *Night*. The two lit modes capture the game's depth buffer and ray-march against it: a procedural sky where nothing was drawn (sun, haze and drifting clouds by day; stars, moon and halo by night), a shadow ray from every surface toward the sun or moon, volumetric light shafts, distance haze, and at night reflections of the neon traced off the lane. The sun and moon are fixed in the world, so they stay put while the lane rolls. Lighting and styles combine (Synthwave at night, CRT in the sun).
- **Dev mode.** Type `devmode` on the page and a password box appears; with the dev-mode password you can ask Claude Code to change the page. The request runs on a sandboxed clone on the owner's Raspberry Pi within a token budget (10% of the account's daily allowance), the result is validated, the version being replaced is frozen in the Version list, and the new one is pushed here. The password is never in this repository: only its scrypt hash lives on the Pi. Details, containment and setup: [`edit-server/README.md`](edit-server/README.md). When the service is offline the box says so.

## How the stack works

The game logic is a set of PlayMaker state machines inside the Unity WebGL build, and Unity's `SendMessage` bridge lets the page switch their states by name (`SetState`). The mod spawns each hidden course directly: the Sphere's `Restart Game` state puts the ball and the spawn point back at the origin, the spawner's `spawn go tunnel run` state drops a start section there and `Check score` generates one lap per call (the spawner's own per-speed-up path, so laps go easy, medium, hard like a real run). The last course goes through the game's own `resetGame` restart so the game state is clean. Nothing on that path removes old blocks.

Clearing and restarting instantly is the tricky part. A death queues a `death complete` broadcast three seconds later, which is what despawns the course and freezes time at the game-over screen; a restart issued before it lands defuses it, so the mod restarts half a second after a death, then despawns everything through the spawner's `DestroyBlocksPool` state (forcing `start game` in the same frame, because that state also stops time and the despawn only executes once time runs), rebuilds the stack and restarts again. The draw list and the WebAudio music track are the only signals the mod reads back from the game.

## The shader system

`TemplateData/shaders.js` runs the visual styles. Every `requestAnimationFrame` callback is wrapped, so when Unity's frame callback returns the finished frame sits in the canvas; the mod copies it into a texture (`copyTexSubImage2D`), runs it through the selected style's chain of full-screen passes (full-size and half-size ping-pong buffers, the bloom at half size) and the last pass draws back onto the canvas before the browser composites it. The game's own shaders are never touched. Unity caches GL state and skips redundant calls, so every piece of state the passes use (program, framebuffers, buffers, vertex array, texture units, viewport, scissor/blend/depth/stencil/cull/colour mask) is read before and restored after them; the raw GL entry points are captured before `mod.js` wraps the same prototypes to count the game's draw calls, so the passes are invisible to it.

A style is a list of passes, each naming a fragment shader, the buffer it reads, an optional second input, the buffer it writes and parameters; new styles are a few lines (`SlopeShaders.define(id, {name, passes})` from the console or the community editor works at runtime). The GLSL is ES 1.00 so it runs on WebGL 1 and 2. A shader that fails to compile disables only its style and is counted in `SlopeShaders.stats()`, which also reports the frames presented, the passes drawn, GL errors and the CPU time of the last pass. The intensity slider blends each style with the untouched frame. The ball's speed (`SlopeMod.speed()`) drives *Hyperspeed*.

Lighting is a second stage in front of the styles. While *Sunny* or *Night* is on, the game's binds of the default framebuffer are redirected to an offscreen framebuffer with a depth-stencil texture (the game binds it four times a frame and never reads the binding back, so it cannot tell), and the passes read that colour and depth directly instead of copying the canvas. Unity uploads its view-projection matrix (`unity_MatrixVP`) every frame as four vec4s; from it the mod recovers the near and far planes, the field of view and the camera's orientation in the world, which makes the depth reconstruction exact and lets the sun and moon live in world space. Per pixel the lighting pass reconstructs the view-space position and normal from depth, shades the dark faces as a grey (day) or wet-asphalt (night) surface under the neon, marches a shadow ray toward the light through the depth buffer, and at night marches a reflection ray off the lane; a half-size pass marches toward the light through the sky mask for light shafts. `SlopeShaders.camera()` shows what was recovered. On WebGL 1 without `WEBGL_depth_texture` the lit modes still run, without shadows and reflections.

The previous system rewrote every fragment shader of the game at compile time to recolour the green: it could only change pixel colours, it failed shader by shader, it uploaded a uniform before every draw call, and nothing about it could change once the shaders were compiled.

`tools/shader_check.py` (needs `playwright`, like `bench_load.py`) serves the repository, starts a run in headless Chromium, switches through every style and checks for each that frames are presented, no GL error or shader failure is counted, the screenshot differs from *Classic* and the ball keeps advancing, then switches back to *Classic* and checks the game still runs; it writes a screenshot per style.

## Hosting your own copy

Fork this repository, open **Settings → Pages**, set the source to the `mod` branch (root), and the game will be served at `https://<your-user>.github.io/Slope-Game/` after a minute or two. If a network blocks the URL, renaming the repository changes it. There is no build step; it is static files.

## Load time

`Build/slope_data.unityweb` (the scene data, 8.6 MB raw) is stored gzip-compressed with the comment marker Unity's loader looks for (`UnityWeb Compressed Content (gzip)`; `unityloader41.js` only inflates a gzip stream that carries it and passes any other file through untouched, so a plain `gzip` would break the load). GitHub Pages does not compress `.unityweb` files itself, so this cuts the first-visit download from about 14 MB to 8 MB; `tools/unitygz.py` compresses or decompresses a bundle, `tools/pack_webdata.py` writes the compressed form by default (`--raw` for the old one) and `tools/unpack_webdata.py` reads either. `Build/slope.json` also turns on the loader's IndexedDB cache (`cacheControl: must-revalidate`): a repeat visit sends conditional requests for the three engine files, gets `304 Not Modified` back and reads them from the cache, about 0.3 MB of transfer instead of 8 MB, independent of the browser's HTTP cache evicting them. `tools/stackfreeze.py` (needs `playwright`) is the soak test for the stacked-course and game-over freezes: it plays a stack of N courses with the mod's lane-centering autopilot and reports lap spawn bursts, frame gaps, a stalled ball and every console error, and `--audit` lists the heap candidates per variable by class. `tools/bench_load.py` (needs `playwright`) serves the repository locally, loads the page in headless Chromium at a chosen bandwidth, reports the bytes and the time to the menu, then starts a run on a curved track to prove the game plays; `--runs 2 --profile DIR` shows the second visit served from the cache.

## Versions

The page at the site root is always the latest version. Older releases are complete copies under `versions/<tag>/`, listed in `versions/index.json`, and the Mod Menu's **Version** selector (`TemplateData/versions.js`) switches between them; an old version shows a note with a link back to the latest. A snapshot shares the engine files, the loader and the music tracks with the root when they are byte-identical (those files have not changed since the fork and must not be removed or modified in place; a changed file is copied into the snapshot instead), so each one costs about 9 MB on the site and nothing in the repository when its files are already in the history. Because every snapshot is self-contained, a broken latest version never takes the older ones down: players just pick one that works.

To freeze the version you are about to replace, before publishing a risky change:

```
python3 tools/snapshot_version.py v7-slabs --from HEAD --title "Three-slab geometry" --notes "..."
python3 tools/snapshot_version.py --latest --title "What the root version is now"
```

Every version that has been live is kept, including broken ones (the picker is how a player escapes a bad latest version): `v4-stack`, `v5-gravity`, `v6-track`, `v7-slabs`, `v8-gapwrap`, `v9-forward`, `v10-fastload`, `v11-nofreeze`, and so on. The rule is enforced by `.githooks/pre-push` (install once per clone with `git config core.hooksPath .githooks`): a push to `mod` is refused while the version it replaces, the remote's current head, is not in `versions/index.json` (by commit hash, or by having the same `index.html`, `TemplateData` and `Build` trees as a listed version, or by the push changing no game file at all, so a commit that only touched the versions, the tools or this file needs no snapshot of its own).
