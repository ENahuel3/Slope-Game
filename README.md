# Slope (modded)

**Play it here: https://enahuel3.github.io/Slope-Game/**

A modded fork of [cgolden15/Slope-Game](https://github.com/cgolden15/Slope-Game), which is a self-hostable copy of the Slope game by Y8 Games / IDnet. This fork lives on the `mod` branch and is what GitHub Pages serves.

## What the mod changes

- **No ads, no tracking.** The page shell is a plain HTML5 document with the ad slots, analytics and promo banner removed, and `TemplateData/mod.js` blocks the game's own calls to the id.net / y8 / Unity Analytics backends before they leave the browser. The in-game app-store button and the Y8 "more games" branding are disabled inside the scene data (`Build/slope_data.unityweb`). A stray token at the end of `unityloader41.js` that threw a `ReferenceError` on every load is fixed.
- **Mod Menu.** All controls live inside **Mod Menu**: Courses, Style and intensity, Light, Music, Track, Mort, King Julien, Version and Fullscreen. The compact menu button stays visible during play. The menu supports keyboard navigation, Escape, and small screens. Preferences persist in the browser.
- **Stacked courses, instantly.** Type a number into **Courses** and every run starts with that many random courses sitting exactly on top of each other: the rapid-Enter restart glitch turned into a feature, built in a fraction of a second while the ball is still dropping into the start tunnel. Changing the number applies at the next restart. The stack applies on a straight track only: hidden courses are built in one frame and cannot follow a rolled lane, so with *Curves* or *Twists* on, the number is dimmed and one course is played (the straight hidden lanes used to cut through the rolled lane and wedge the ball).
- **Instant restarts.** Press **R** at any time to restart with a fresh stack. When the ball dies the mod shows the death for half a second and restarts with the stack rebuilt; there is no game-over screen and no Enter to press. With Courses set to 1 a death goes through the normal game-over screen. A ball that cannot move forward (wedged between two stacked courses at a section drop, where it sits alive in the gap, or in a kink of a rolled lane) never dies, so in a stack or a track mode the mod restarts the run after 1.5 s without forward movement, or after 2 s of creeping (under 5 units/s along the course, a ball wedged between a rolled lane and a hidden straight one), like a death; a plain single-course game is left alone. The watchdog allows four seconds after startup regardless of refresh rate and ignores hidden tabs or frame gaps, so loading or returning to the tab cannot falsely reset a run. Late music-start confirmations do not rebuild an already-live stack.
- **Music.** Original, *Aria Math (Phonk Remix)*, *Mort Jackson – Billie Jean* or *Epic Sax Gandalf* (Ukes of Hazzard). A custom track keeps its place across restarts (it pauses when the game would stop its own track and resumes when a run starts), and switching mid-run is immediate.
- **Track shaping.** The course rolls about its own centre line, as real, continuous geometry. *90° twists* roll a quarter turn over twenty blocks; *Curves* roll 120 to 240 degrees, one block at a time, so you ride up onto what was the wall, over the ceiling and back. Two copies of the lane-block prefab are added to the scene bundle whose surface and neon walls are helicoids twisting by exactly +4.5° / -4.5° from start to end (`tools/patch_roll.py`, meshes generated from the block's shape, collision cooked at runtime), so a run of them is one smooth ribbon and the next block starts where the last ended. The spawner's lane-block spawns take their prefab from a new FSM GameObject variable (`ModBlock`); the mod decides for each upcoming block whether it is flat or a helicoid in either direction and writes that prefab's object pointer, together with the block's start rotation (`ModQ1` and the spawn transform), before the block is spawned. Every spawner step is gated so exactly one step runs per mod frame while a track mode is on, whatever Unity's update rate: the step takes its `Wait` time from `ModHold` (0 = the vanilla one-frame burst, which stacking relies on; 1000 s = hold) and the mod releases one step per frame by zeroing it; a `ModMark` flag tells the mod which steps spawned a helicoid-capable block so the roll only advances across those (tilted, thin and dogleg pieces stay rigid at the roll they were spawned at). The ball's frame follows the built course exactly: each block record carries its start and end roll, gravity, the forward push and steering are rotated into that frame through the WebAssembly heap, and native camera actions follow the current ball position with a rotated offset and quaternion in LateUpdate, so the view stays aligned through twists and rolls (`tools/patch_camera.py`). `tools/patch_spawner.py` / `tools/patch_rotations.py` make every block copy the spawner's rotation, `tools/patch_sections.py` splits the spawner's section states into one step per block, `tools/patch_triggers.py` repairs the checkpoint triggers for the rolled spawn frame, and `tools/fsmparse.py` / `tools/fsmwrite.py` are the PlayMaker FSM parser and serializer behind all of it. The HUD **Track** selector offers Straight, Curves, 90° twists, or both. The roll never pauses: every course piece has its own helicoid copies now, not only the lane block. `tools/twist_mesh.py` twists any mesh with the lane block's rule (the cross-section at course coordinate *t* rotates by 4.5° × *t* / 14.1421 about the lane's centre line, after slicing the triangles every 1.77 units so long edges follow the helix), and `tools/patch_twist_pieces.py` makes +4.5° / −4.5° copies of the speed-arrow block, the tilted lanes, the thin lanes, the dogleg, the jump lips, the tunnels and their roofs, re-points the lane block's own helicoids at the same twist of the real Slope mesh, and gives the spawner a `ModTw<Piece>` GameObject variable per piece (with `Flat` / `P` / `N` siblings) that every spawn of that piece reads. The spawner now holds *between* moving its spawn point and spawning there, and each hold publishes `ModMark` (the length along the course of the floor piece about to spawn) and `ModSpan` (how far anything spawned there reaches, e.g. a tunnel arch over the next blocks): the mod sets the piece's start roll knowing where it starts and how long it is, and the roll runs through tilts, thin lanes, doglegs, tunnels and jump lips as one continuous helix. A 90° twist still lands within half a block's roll of 90°: a piece that would overshoot is spawned flat and the twist resumes with the next piece that fits, and whatever overlaps a twisted or a flat piece follows it. A slow curve runs the full nominal distance and lets its last piece finish its own twist. The obstacles follow the roll too: the game placed and animated them in world space (the sliding red block tweens +10 along world x, the three rising blocks +20 along world y, the death towers are moved ±20 / +10 in world x / y after spawning, and the mover and the second and third rising blocks spawn at a world-space offset of the spawn point), which on a rolled lane sent them along axes that were no longer the lane's. `tools/patch_obstacles.py` moves those tweens and translates to Self space with the vectors re-expressed in the spawn frame, turns the spawn offsets into a Self-space Translate of the spawned object, and disables the death tower's own world-space SetRotation, so every obstacle sits and moves in the frame of the block it stands on.
- **Scenery toggles.** Turn **Mort** on to show a crowd of Mort from Madagascar with any soundtrack. With Mort off, Aria Math shows a horde of Minecraft's own zombie (the game's geometry and skin, see `tools/assets/zombie/README.md`), *Epic Sax Gandalf* lines the lane with Gandalf himself (an upright cut-out picture card per skyline slot, `tools/assets/gandalf/README.md`, built by `tools/patch_gandalf.py`), and other tracks show the original pillars. Mort now uses the textured [Mort V2 model by calvinwil5782](https://sketchfab.com/3d-models/mort-v2-763eecc8409145059cff213fa646d4cd), under CC BY 4.0, with its original face/body, tail and hair textures. It replaces the stylized Warehouse model and the earlier procedural spheres. Character: DreamWorks Animation. There are 87 Morts per chunk, using three staggered instances of the 29-figure mesh to stay within the engine's 16-bit mesh limit without tripling the download; every Mort stands 240 units from the lane center on either side and turns 20° inward toward it; zombies keep their neon-outline material. The independent **King Julien** toggle puts his PNG face/crown inside every red obstacle border, or restores plain red textures immediately, with any soundtrack. PNG source and implementation: [`TemplateData/themes/julien/README.md`](TemplateData/themes/julien/README.md). The Mort setting and music choose the prefab through the existing `ModBuilding` FSM variable; new figures appear in newly spawned chunks, or after restarting. Model attribution and rebuild instructions: [`tools/assets/mort/README.md`](tools/assets/mort/README.md).
- **Leaderboard.** The game's own leaderboard was an id.net panel that never initialises any more (the white "Register to submit" box). It is replaced by a working one: scores live on the mod's own server (`edit-server/server.js`, `/api/scores` on the same host as dev mode, one best run per name, no account), and the board is drawn the way the game's menu is drawn, with the game's own 6809CHAR dot-matrix font (`TemplateData/fonts/`, extracted from the scene bundle), `#00ff00` on black, 2 px outlined boxes sized from the game canvas like the Unity canvas scaler. On game over the board appears exactly where the id.net panel was, with the top ten, your rank and best, and a name entry; the run's score (coins included) is sent once a name is set. **L** opens and closes it whenever the game is not running, and before the first run a matching box covers the title menu's own Leaderboard button. `TemplateData/leaderboard.js`.
- **Super ramps.** Now and then a lane block carries an orange wedge with chevrons on it. Run onto it and the ball is shoved to five times its speed and launched into the air, flying a long way down the course before it lands (measured: about 35 units up and some 250 units along). The ramp is the mod's own: `TemplateData/ramps.js` lays it out in the lane frame of a block that `coins.js` has recognised, draws it into the game's frame, and fires the launch by writing the game's own push variables for a fraction of a second (`SlopeMod.boost`: `zforce` forward until the speed target, `yforce` upward for a quarter second). Ramps never sit in the start tunnel, under a roof, on a rolled block, right in front of the ball, or within nine blocks of the previous one; a ramp block loses its edge coin. The **Super ramps** toggle in the Mod Menu turns them off.
- **Coins.** Collectable 3D coins sit in the places that are hard to reach but reachable, every position derived from the piece meshes and the ball physics (`tools/coin_layout/README.md`): on the ridge of the red-striped arch tunnels and on the beam atop the death tunnel's stepped roof (a ball lands there off a gap lip), on the lip of each jump and just past it in the air where every speed's trajectory passes, at the edges of the thin lanes, on the uphill side of the tilted lanes, at the outer corners of the doglegs, and at the very edge of one lane block in three (never under a tunnel, and never in the start tunnel). Each coin is one point on the game's own score; the **Coins** toggle in the Mod Menu turns them off. The coin is plaggy's CC0 "gold coin blank" from OpenGameArt (`tools/assets/coin/README.md`), drawn the way games did around 2000: per-vertex Gouraud lighting with a hard specular, an unfiltered 128 px texture, spinning and bobbing in place, with a square-wave two-note chime when picked up. `TemplateData/coins.js` finds the pieces without touching the scene: every track piece is its own draw call with its own object-to-world matrix, and the vertex buffers are uploaded byte for byte from the scene data, so each mesh is recognised by the size and a hash of its upload (`tools/mesh_fingerprints.py`); a piece's coins are laid out in its own lane frame and transformed by its matrix, so they follow a rolled or shifted piece exactly, and the ball (another draw call) gives the position for collecting and the camera for drawing. The coins are drawn into the game's frame after its draws and before the post-processing (`SlopeShaders.onScene`), depth-tested against the lane and the tunnels. One thing in the scene data changed for this: Unity's dynamic batching is turned off (`tools/patch_batching.py`), because it merged the small lane meshes, the jump gap, the thin and the tilted lanes into per-frame combined buffers that no longer named their pieces. `tools/coin_check.py` is the harness: it checks that pieces are recognised, coins are generated and drawn without GL errors on WebGL 1 and 2 and under the lit modes, that a coin planted on the ball's line is collected, and with `--watch` it photographs the coins on each piece kind as the ball reaches it.
- **Visual styles.** *Classic*, *Rainbow* (the green neon becomes a diagonal rainbow that scrolls across the screen and ripples with a travelling wave; red stays red), *Neon glow* (bloom), *Synthwave* (magenta/cyan grading, glow, chromatic fringe, faint scanlines), *CRT arcade* (curved screen, scanlines, phosphor mask), *Hyperspeed* (radial blur and colour split that grow with the ball's speed), *Pixel* (chunky dithered pixels), *Noir* (black and white with the red obstacles kept) and *Matrix* (green phosphor). They are post-processing passes over the finished frame; see *The shader system* below.
- **Lighting.** *Normal*, *Sunny* or *Night*. The two lit modes capture the game's depth buffer and ray-march against it: a procedural sky where nothing was drawn (sun, haze and drifting clouds by day; stars, moon and halo by night), a shadow ray from every surface toward the sun or moon, volumetric light shafts, distance haze, and at night reflections of the neon traced off the lane. The sun and moon are fixed in the world, so they stay put while the lane rolls. Lighting and styles combine (Synthwave at night, CRT in the sun).
- **Dev mode.** Type `devmode` on the page and a password box appears; with the dev-mode password you can ask Claude Code to change the game. The request runs on a sandboxed clone on the owner's Raspberry Pi, where Claude can edit the page code, the tools and the scene bundle, and can run the game itself headless (`tools/smoke_check.py` and the other harnesses) to test what it changed; before anything is published the server loads and plays the page once more and discards an edit that breaks it, the version being replaced is frozen in the Version list, and the new one is pushed here. The password is never in this repository: only its scrypt hash lives on the Pi. Details, containment and setup: [`edit-server/README.md`](edit-server/README.md). When the service is offline the box says so.

## How the stack works

The game logic is a set of PlayMaker state machines inside the Unity WebGL build, and Unity's `SendMessage` bridge lets the page switch their states by name (`SetState`). The mod spawns each hidden course directly: the Sphere's `Restart Game` state puts the ball and the spawn point back at the origin, the spawner's `spawn go tunnel run` state drops a start section there and `Check score` generates one lap per call (the spawner's own per-speed-up path, so laps go easy, medium, hard like a real run). The last course goes through the game's own `resetGame` restart so the game state is clean. Nothing on that path removes old blocks.

Clearing and restarting instantly is the tricky part. A death queues a `death complete` broadcast three seconds later, which is what despawns the course and freezes time at the game-over screen; a restart issued before it lands defuses it, so the mod restarts half a second after a death, then despawns everything through the spawner's `DestroyBlocksPool` state (forcing `start game` in the same frame, because that state also stops time and the despawn only executes once time runs), rebuilds the stack and restarts again. The draw list and the WebAudio music track are the only signals the mod reads back from the game.

## The shader system

`TemplateData/shaders.js` runs the visual styles. Every `requestAnimationFrame` callback is wrapped, so when Unity's frame callback returns the finished frame sits in the canvas; the mod copies it into a texture (`copyTexSubImage2D`), runs it through the selected style's chain of full-screen passes (full-size and half-size ping-pong buffers, the bloom at half size) and the last pass draws back onto the canvas before the browser composites it. The game's own shaders are never touched. Unity caches GL state and skips redundant calls, so every piece of state the passes use (program, framebuffers, buffers, vertex array, texture units, viewport, scissor/blend/depth/stencil/cull/colour mask) is read before and restored after them; the raw GL entry points are captured before `mod.js` wraps the same prototypes to count the game's draw calls, so the passes are invisible to it.

A style is a list of passes, each naming a fragment shader, the buffer it reads, an optional second input, the buffer it writes and parameters; new styles are a few lines (`SlopeShaders.define(id, {name, passes})` from the console or the community editor works at runtime). The GLSL is ES 1.00 so it runs on WebGL 1 and 2. A shader that fails to compile disables only its style and is counted in `SlopeShaders.stats()`, which also reports the frames presented, the passes drawn, GL errors and the CPU time of the last pass. The intensity slider blends each style with the untouched frame. The ball's speed (`SlopeMod.speed()`) drives *Hyperspeed*.

Lighting is a second stage in front of the styles. While *Sunny* or *Night* is on, the game's binds of the default framebuffer are redirected to an offscreen framebuffer with a depth-stencil texture (the game binds it four times a frame and never reads the binding back, so it cannot tell), and the passes read that colour and depth directly instead of copying the canvas. Unity uploads its view-projection matrix (`unity_MatrixVP`) every frame as four vec4s; from it the mod recovers the near and far planes, the field of view and the camera's orientation in the world, which makes the depth reconstruction exact and lets the sun and moon live in world space. Per pixel the lighting pass reconstructs the view-space position and normal from depth, shades the dark faces as a grey (day) or wet-asphalt (night) surface under the neon, marches a shadow ray toward the light through the depth buffer, and at night marches a reflection ray off the lane; a half-size pass marches toward the light through the sky mask for light shafts. `SlopeShaders.camera()` shows what was recovered. On WebGL 1 without `WEBGL_depth_texture` the lit modes still run, without shadows and reflections.

The previous system rewrote every fragment shader of the game at compile time to recolour the green: it could only change pixel colours, it failed shader by shader, it uploaded a uniform before every draw call, and nothing about it could change once the shaders were compiled.

`tools/shader_check.py` (needs `playwright`, like `bench_load.py`) serves the repository, starts a run in headless Chromium, switches through every style and checks for each that frames are presented, no GL error or shader failure is counted, the screenshot differs from *Classic* and the ball keeps advancing, then switches back to *Classic* and checks the game still runs; it writes a screenshot per style.

## Frame pacing

**Render quality → Automatic** is the default. During live play it caps the initial drawing buffer at about 1.2 million pixels and reduces it further when sustained slow rendered frames exceed the budget. It recovers slowly when the frame rate is stable. The canvas stays full-screen; only game sharpness changes, and title/game-over menus and the HTML settings stay at native resolution. Choose **Full resolution** to keep every screen pixel. **Show FPS** reports browser-frame timestamps for actual Unity scene draws and the 1% low over the last 300 rendered frames. Animation callbacks without a draw are excluded; CPU submission-phase jitter within one frame is not treated as a missed frame.

Straight tracks now release one spawn step per frame instead of constructing an entire section in one burst. Extra render-distance sections wait for the spawner to stop moving before starting another section. Hidden stacked-course construction keeps its original burst behavior. The overlays mirror state written by both Unity and their own GL setters, avoiding synchronous state-query round trips during ordinary frames; object deletion and context restoration invalidate the affected cache. Ramp geometry is static and batched, with its own VAO where available.

`tools/frame_bench.py` samples frame-boundary timestamps for actual scene draws in Chromium or Firefox, reports mean FPS, 1% low (the reciprocal of the mean of the slowest 1% of intervals), p99 and worst frame time, and can load baseline scripts from a git revision. Use `--gpu --browser firefox --width 1920 --height 1200 --light night --view-distance 10` for the heavy test. Headless browser, random course, browser-version and thermal differences mean this does not guarantee a particular frame rate on every machine. Run only one browser test at a time, with `nice -n 19 taskset -c 0-5`, to avoid competing with live play.

Deterministic checks: `node tools/performance_check.js`, `node tools/ramp_batch_check.js`. Browser checks: `tools/gl_state_check.py` compares the mirror against native WebGL 1/2 state, including deletion and context restoration; `tools/performance_browser_check.py` checks pointer input, steering, native/automatic switching, window resizing and restarts (`--webgl1` exercises the extension path).

## Hosting your own copy

Fork this repository, open **Settings → Pages**, set the source to the `mod` branch (root), and the game will be served at `https://<your-user>.github.io/Slope-Game/` after a minute or two. If a network blocks the URL, renaming the repository changes it. There is no build step; it is static files.

## Load time

`Build/slope_data.unityweb` (the scene data, 8.6 MB raw) is stored gzip-compressed with the comment marker Unity's loader looks for (`UnityWeb Compressed Content (gzip)`; `unityloader41.js` only inflates a gzip stream that carries it and passes any other file through untouched, so a plain `gzip` would break the load). GitHub Pages does not compress `.unityweb` files itself, so this cuts the first-visit download from about 14 MB to 8 MB; `tools/unitygz.py` compresses or decompresses a bundle, `tools/pack_webdata.py` writes the compressed form by default (`--raw` for the old one) and `tools/unpack_webdata.py` reads either. `Build/slope.json` also turns on the loader's IndexedDB cache (`cacheControl: must-revalidate`): a repeat visit sends conditional requests for the three engine files, gets `304 Not Modified` back and reads them from the cache, about 0.3 MB of transfer instead of 8 MB, independent of the browser's HTTP cache evicting them. `tools/stackfreeze.py` (needs `playwright`) is the soak test for the stacked-course and game-over freezes: it plays a stack of N courses with the mod's lane-centering autopilot and reports lap spawn bursts, frame gaps, a stalled ball and every console error, and `--audit` lists the heap candidates per variable by class. `tools/bench_load.py` (needs `playwright`) serves the repository locally, loads the page in headless Chromium at a chosen bandwidth, reports the bytes and the time to the menu, then starts a run on a curved track to prove the game plays; `--runs 2 --profile DIR` shows the second visit served from the cache.

## Versions

The page at the site root is always the latest version. Older releases are complete copies under `versions/<tag>/`, listed in `versions/index.json`, and the Mod Menu's **Version** selector (`TemplateData/versions.js`) switches between them; an old version shows a note with a link back to the latest. A snapshot shares the engine files, the loader and the music tracks with the root when they are byte-identical (those files have not changed since the fork and must not be removed or modified in place; a changed file is copied into the snapshot instead), so each one costs about 9 MB on the site and nothing in the repository when its files are already in the history. Because every snapshot is self-contained, a broken latest version never takes the older ones down: players just pick one that works.

To freeze the version you are about to replace, before publishing a risky change:

```
python3 tools/snapshot_version.py v7-slabs --from HEAD --title "Three-slab geometry" --notes "..."
python3 tools/snapshot_version.py --latest --title "What the root version is now"
```

Every version that has been live is kept, including broken ones (the picker is how a player escapes a bad latest version): `v4-stack`, `v5-gravity`, `v6-track`, `v7-slabs`, `v8-gapwrap`, `v9-forward`, `v10-fastload`, `v11-nofreeze`, and so on. The rule is enforced by `.githooks/pre-push` (install once per clone with `git config core.hooksPath .githooks`): a push to `mod` is refused while the version it replaces, the remote's current head, is not in `versions/index.json` (by commit hash, or by having the same `index.html`, `TemplateData` and `Build` trees as a listed version, or by the push changing no game file at all, so a commit that only touched the versions, the tools or this file needs no snapshot of its own).
